# Feature API と内部 Composition — 設計原則（Draft）

**目的:** Host・Account・Profile 等が Feature の公開 API を構成し、Feature が内部の実装を自由に組み合わせられるようにする。

## 原則

1. **公開 API は利用側が設定するためのもの。** Host 等による上書きは正規の利用方法であり、Nix module の通常の優先順位で合成される。Feature は最終的な API 値に従う。
2. **Feature は目的と振る舞いを公開し、実装詳細を隠す。** 公開された選択肢を利用するために、Host が内部の `programs.*` や `services.*` を直接編集する必要はない。
3. **内部実装は合成・交換可能にする。** 同じ役割を果たせる実装が複数ある場合、Feature は選択可能な Provider を利用してよい。ただし Provider Registry や Capability 階層は必須ではない。実際の交換可能性がないなら直接 Program を使用してよい。
4. **公開 API の意味と実効構成を一致させる。** Feature がある能力の提供を約束するなら、選ばれた実装がその能力を満たす必要がある。矛盾を検出する方法は各 Feature で決める。自動フォールバックは要求しない。
5. **Feature の無効化は、共有 Program の排他的な無効化ではない。** `feature.enable = false` は原則としてその Feature からの構成を停止する。他の利用者が同じ Program を使うことを妨げない。個別の子オプションの `false` が何を禁止・停止するかは、その API の説明で明示する。

## 適用時の確認事項

- 利用者は公開 API だけで、意図した構成差分を表現できるか。
- Feature が要求する振る舞いと、内部の有効な構成は一致しているか。
- Provider を導入する場合、その役割と必要な操作が明確で、代替可能性を説明できるか。
- 無効化時、他の Feature が共有する Program を不必要に壊さないか。
- Feature が権限を制御する場合、どの権限を管理するかと、`false` の保証範囲が明示されているか。

## この文書で決めないこと

共通 Provider Framework、全 Program の単一所有者、全 Feature の API 形状、ターゲット間の設定同期方式、具体的な移行順序は決めない。Home Manager と NixOS は別々に評価されるため、同名オプションを持つことだけで同期されるとはみなさない。

この文書は**設計判断の基準**であり、既存 Nix コードの変更や一律の移行手順を指示するものではない。
